# Clawdmeter session history

Moved verbatim from CLAUDE.md's "Recent session highlights" (2026-10-17) to keep the
always-loaded CLAUDE.md small. This is the *why* behind the current design -- read the
relevant entry before reworking WiFi/BLE-removal, memory, theming, security or discovery.
The actionable rules distilled from it live in CLAUDE.md's gotchas and the `.claude/skills/`.


- Originally targeted Waveshare ESP32-S3-Touch-AMOLED-2.16 (480×480, CO5300, PSRAM, IMU, touch, PMU). See git history for that version.
- **Ported to ideaspark ESP32 1.14" ST7789** (135×240, no PSRAM, no IMU, no touch, no PMU). Full hardware swap: SPI display driver, stub power/IMU, complete UI layout redesign for 135×240, LVGL buffers in SRAM.
- pioarduino platform retained (needed by GFX Library 1.6.x for `esp32-hal-periman.h`); switched board from `esp32s3box` → `esp32dev`.
- Flash usage was tight (~90%) right after the port; has since eased as the partition scheme/build settled (~63% as of 2026-09-11) — see gotcha #5, don't trust either number without checking `pio run`'s own report.

- **Sensor trend graphs** (`sensor_hist.{h,cpp}` + the `SCREEN_SENSOR_GRAPH` page in `ui.cpp`): 24 h of temp/humidity/pressure in a 96-slot × 15-minute ring, mean-averaged per slot, flushed to NVS (namespace `shist`, key `ring`, 588-byte blob) on every slot roll so the trend survives a reboot. The Sensor page carries a temperature sparkline; the "Trend 24h" page stacks one auto-scaled panel per metric. Traces are `lv_line` polylines, not `lv_chart` — `LV_USE_CHART` is not in `platformio.ini` and the polyline costs no extra flash.
- **No RTC on this board**, so the ring is indexed by absolute 15-minute buckets derived from the daemon's `{"src":"env"}` epoch. Until that arrives it free-runs on `millis()`; `sensor_hist_set_time()` re-anchors the ring and rolls it forward over the power-off gap. Serial QA commands: `histfill` (synthetic 24 h trace) and `histclear`.
- **Added Clock, SysInfo, VS Code, CI, and Today screens** (`SCREEN_CLOCK`/`SCREEN_SYSINFO`/`SCREEN_VSCODE`/`SCREEN_CI`/`SCREEN_TODAY`) — see the Screens table above for what each shows and its payload `src`. Clock is the effective "home" screen (first stop after Splash) and doubles as a focus-timer display.

The focus timer reuses the same widget for a transient 4 s "Focus"/"Break time" message (`banner_auto_hide_ms`).

- **Navigation/alerting/UI pass** (2026-09-11 session — analyze-and-improve pass across navigation, alerting, visual polish, and usage-history trends):
  - **Screen-position dots** — a row of small dots near the top of the screen, shown for 1.5 s after every `ui_show_screen()` then auto-hidden (`ui.cpp`: `dot_objs`/`refresh_screen_dots()`/`dots_hide_ms`, ticked in `ui_tick_anim()`). Position is computed against `CYCLE_ORDER[]`, which mirrors `ui_cycle_screen()`'s traversal order — keep the two in sync if the cycle order ever changes. `screen_is_populated()` is the single shared predicate for "has this screen ever received data" (used by both the dots and the cycle-skip logic — don't reintroduce a second copy).

It's a ranking, not a stack: a pre-empted lower-priority banner is dropped, not restored, when the higher one clears — see the comment above `banner_kind_t` before changing this. `BANNER_ALERT` is shared by CI-failure (`ui_update_ci()`) and the session/weekly ≥90% usage alert (`ui_update()`, `USAGE_ALERT_PCT`), each with its own one-shot "armed" flag so a payload doesn't re-fire the banner every poll.

Deliberately not a "wait to see if a second press follows" implementation (that would make every single press feel laggy with up to 10 screens in the cycle) — the first press always cycles immediately; a fast second one just redirects.
  - **Agent-count badge** — `g_act_agents` (from `{"src":"act"}`'s `n` field) was tracked but never rendered before this; now shown as "xN" left of the activity dot when N > 1 (`lbl_agent_badge` in `refresh_status_label()`).

Backed by `usage_hist.{h,cpp}`, fed every `ui_update()` call (`usage_spark_rebuild()`), sampled in `main.cpp`'s "claude" payload branch.
  - Fixed `lbl_anim`'s (Usage screen gerund spinner) text overflow: the longest words ("Philosophising…", "Flibbertigibbeting…") used to run off the 135px width uncropped — now `LV_LABEL_LONG_DOT` truncates with "...".

- **WiFi + HTTP dashboard, Phase 1 of 3** (2026-09-15 session — additive to BLE, not a replacement; see the plan this was built from for the full 3-phase scope). Landed: `wifi_net.{h,cpp}` (STA connectivity, credentials provisioned over the existing BLE RX channel via a new `{"src":"wifi","ssid":...,"pass":...}` case in `process_payload()`, daemon-side one-shot push in `Session.push_wifi_credentials()`), `web_server.{h,cpp}` (`GET /`, `GET /api/state`, `GET /api/screenshot.bmp` — no auth yet, no mutating routes yet), `device_api.h` (`build_state_json()`/`capture_screenshot_rgb565()`, implemented in `main.cpp`), `tools/web_ui/index.html` + `tools/build_web_ui.js` → `web_ui.h` (gzip'd PROGMEM page, same generated-header convention as `splash_animations.h`).   - **This session hit three separate, genuinely hard-to-diagnose bugs while landing it** — all now fixed and captured as CLAUDE.md gotchas #11-13 above; read those before touching WiFi/NVS/LVGL memory config again. In order of discovery: (1) the DRAM link-budget overflow that motivated the partition-table rewrite (gotcha #12's partition half) and an initial (wrong) fix attempt of shrinking `LV_MEM_SIZE`; (2) a `Preferences` read-only-open-on-new-namespace crash (gotcha #11); (3) the real fix for the `lv_timer_handler()` hang — switching LVGL off its fixed pool entirely (gotcha #13), which is the one to remember: **don't re-introduce `LV_MEM_SIZE`/`LV_USE_STDLIB_MALLOC=LV_STDLIB_BUILTIN` on this board without re-verifying every screen's first show under `screen <n>`.**
  - **Partition table rewrite** (`firmware/partitions_app.csv`, replaces `min_spiffs.csv`) — dropped OTA (never used) for one ~3.9 MB "factory" app partition instead of two ~1.9 MB OTA slots; `nvs` kept at the exact same `0x9000`/`0x5000` so BLE bonds and `sensor_hist`/`usage_hist` NVS blobs survived the switch.
  - **Shared splash canvas buffer** (`get_shared_canvas_buf()` in `splash.cpp`) — Splash, Copilot, and Aurora canvases now share one buffer (sized to the largest, the 120×120 splash canvas) instead of each permanently holding its own, since the three screens are mutually exclusive. `splash_copilot_show()`/`splash_aurora_show()` (new, called from `ui_show_screen()`) re-render fresh into the shared buffer on entry, since it may hold stale content from whichever of the three was shown last.
  - **`run` project skill** (`.claude/skills/run/SKILL.md`) now documents all of this — build/flash/screenshot workflow plus every gotcha above — load it before re-debugging any of these symptoms from scratch.
- **WiFi memory-budget saga (2026-09-15, later same day)** — attempting to actually connect WiFi for the first time (real credentials, real AP) surfaced a much deeper problem than gotchas #11-13: this board's total heap genuinely can't fit [full 12-screen UI] + [full BLE incl. HID] + [live WiFi] all at once, and every fix attempt just moved *where* the shortfall crashed (see gotcha #14 for the full writeup and the fixes that landed). Net result at the time: `ui_init()`'s eager 12-screen build made lazy (7 data-gated screens build on first real data instead of at boot — a genuine, verified fix, kept regardless of what follows), and `WiFi.mode()`/`WiFi.begin()` both gated behind a conservative heap check so a low-memory condition defers the connect attempt instead of ever crashing — but with the full BLE+UI feature set active, WiFi mostly stayed deferred rather than actually connecting. Resolved by the next entry.
- **Remove BLE entirely, WiFi becomes the sole transport (2026-09-15, same day, follow-up session) — landed, flashed, and verified end-to-end: WiFi actually connects now, first time all session.** Rather than keep chasing headroom for three memory-hungry subsystems, BLE was removed outright: `ble.{h,cpp}` deleted, `NimBLE-Arduino` dropped from `platformio.ini`. This also eliminates the BLE/WiFi radio-coexistence class of bug outright (WiFi has the radio to itself now) and confirmed the HID-keyboard service (`ble_keyboard_press()`/`release()`) was 100% dead code — declared, implemented, never called. Measured result: `RAM: 20.5%→18.1%`, `Flash: 44.3%→39.1%`.
  - **Firmware**: `POST /api/payload` (`web_server.cpp`, token-gated via `X-Auth-Token` matching `wifi_get_token()`) replaces BLE's RX characteristic as the data-ingest path, thin-wrapping the same `process_payload()`/`device_ingest_payload()` dispatcher the serial `feed` command already used — no parsing logic duplicated. **Gotcha discovered while testing**: ESP32 `WebServer`'s `server.arg("plain")` only returns the raw body when the request actually carries `Content-Type: application/json` — a plain `curl -d '...'` (which defaults to `application/x-www-form-urlencoded`) silently gets an empty body and a 400, nothing to do with the token/auth check. The daemon's `httpx` client already sets this header correctly; only hand-rolled `curl` smoke-tests need to remember `-H "Content-Type: application/json"`. `MDNS.begin("clawdmeter")` (ESPmDNS, ships with the core, no new `lib_deps`) added alongside `server.begin()`; verified resolving from a Windows host via `Resolve-DnsName`/`ping` with zero extra setup. Connectivity screen (`init_bluetooth_screen()`, `SCREEN_BLUETOOTH` enum name kept — cosmetic to rename, not worth the diff) lost its Bluetooth icon and 3 BLE status labels; IP/token/mDNS-hostname now get one line each (`CONN_PANEL_H` 124→88) after combining IP+token on one line clipped in testing once a 4-digit last IP octet was involved. Three UI liveness checks that were keyed off `ble_get_state() == BLE_STATE_CONNECTED` (`data_is_live()`, the freshness pill's "offline" branch, the Usage-screen spinner's fallback) had no direct replacement — HTTP push has no persistent "connected" state — so they now key off `ever_data`/data-age (freshness) alone. The Connectivity-screen long-press ("hold to unpair") now calls `wifi_set_credentials("", "")` ("forget this network") instead; the long-press-elsewhere "ask the daemon for an immediate poll" gesture was dropped outright — it's now a no-op beyond the flash feedback. New serial command `token` prints the auth token directly (the on-screen line can be cramped) for scripted setup.
  - **Heap-gate re-measurement (empirical, not assumed)**: post-`ui_init()` max-alloc with BLE removed settled at ~82 KB — real headroom over the ~32 KB that used to be unsafe, but still under the original 90 KB `WIFI_MIN_MAX_ALLOC` bar (which was deliberately calibrated to also survive *concurrent BLE traffic*, a risk that no longer exists). Rather than leave WiFi permanently deferred on an now-obsolete safety margin, `WIFI_MIN_MAX_ALLOC_BEGIN` (the `WiFi.begin()`-specific check) was lowered to 50 KB — comfortably below the measured 82 KB, comfortably above the old unsafe level. `WIFI_MIN_MAX_ALLOC` itself (guarding `esp_wifi_start()`'s one-time driver allocation, a hard requirement independent of BLE) stayed at 90 KB. Confirmed stable afterward: WiFi connected, daemon ran a full real poll cycle (Claude/Copilot/sysinfo/vscode/env/aurora/ci/today all posting successfully) with zero crashes.
  - **Daemon** (`claude_usage_daemon.py`): `Session` rewritten from a `BleakClient` wrapper to an `httpx.AsyncClient` one; `write_payload()` now POSTs instead of a GATT write, `probe()` (a `GET /api/state`) replaces the fast "target unreachable" signal `client.connect()` used to give for free. `push_wifi_credentials()`/the `wifi_ssid`/`wifi_pass` config keys are gone — WiFi provisioning is a one-time manual serial step now (see the Daemon / host side section above), fully decoupled from the daemon. **Found and fixed a real latent bug while testing**: `remember_payload()`/`load_last_payloads()` didn't exclude `src:"wifi"` the way they already excluded `status`/`act` — an old daemon build's cached `{"src":"wifi","ssid":...,"pass":...}` payload (from the since-removed `push_wifi_credentials()`) was still sitting in `~/.config/claude-usage-monitor/last-payloads.json` in **plaintext**, and would have been auto-replayed via `POST /api/payload` on every future reconnect. Both functions now explicitly exclude `wifi`; the existing cache file was scrubbed by hand. **mDNS resolution finding worth remembering**: the `zeroconf` package's `AsyncZeroconf` (checked at 0.151.3) has no direct hostname-resolve call, only `_service._tcp` browsing — adding it as a dependency would've bought nothing, so resolution goes through the OS resolver instead (`asyncio`'s `getaddrinfo`, which delegates to the platform DNS client; Windows 10+/macOS resolve `.local` natively, Linux needs `nss-mdns`/avahi) with a manual `device_host` config-key override as the escape hatch. Same surgical-swap shape as `connect_and_run()`→`run_session()`/`_poll_loop()`: every actual polling interval/orchestration line is untouched, only the connection layer changed.
  - **`daemon/claude-usage-daemon.sh`** (the separate, older, Linux/macOS-only bash+`bluetoothctl` daemon, far fewer features) was **retired, not rewritten** — left in place as an unmaintained historical artifact; `claude_usage_daemon.py` is the documented/canonical daemon.
  - **New: static-memory regression check** (`tools/check_static_mem.py`) — runs `xtensa-esp32-elf-size.exe -A` against the built `.elf` and sums the `.dram0.data`+`.dram0.bss` sections specifically (verified to exactly match `pio run`'s own "RAM: used N bytes" figure), failing if usage exceeds a committed baseline (`tools/static_mem_baseline.json`) by more than a relative delta. **First implementation used `-B` (Berkeley text/data/bss mode) and was wrong** — on this project's Xtensa/ESP32 linker script (separate named sections per memory region: `.dram0.*`/`.iram0.*`/`.flash.*`/`.rtc.*`), Berkeley mode's heuristic lumps `.flash.rodata` (read-only initialized data, ~450 KB here) in with "data", reporting 156% of DRAM on a device that boots fine at 18%. Named-section parsing via `-A` is the only mode that works correctly here. Wired into the `run` skill's build→flash workflow as a mandatory step. **Explicitly a *static*-bloat guard only** — it would not have caught gotcha #14 (static RAM stayed ~20.5% throughout that entire crash-looping saga; the real problem was runtime heap fragmentation). The actual defense against that class of bug remains the runtime heap-gate (`WIFI_MIN_MAX_ALLOC`/`WIFI_MIN_MAX_ALLOC_BEGIN` in `wifi_net.cpp`), which this check doesn't replace.
- **`GET /api/screenshot.bmp` "out of memory" fix (2026-09-16, next-day follow-up)** — a real user-facing bug found the day after the BLE-removal work landed: the dashboard's screenshot `<img>` came up broken because the endpoint's single ~65 KB full-frame `malloc()` was failing under real load (WiFi + an active daemon connection also holding heap) — see gotcha #15 for the full writeup and fix (tile-streaming, matching the serial `screenshot` command's proven approach, plus a negative-height top-down BMP header so no buffering/reversing is needed). `capture_screenshot_rgb565()` was retired in favor of `capture_screenshot_streamed()`; nothing else called the old function, so no compatibility shim was needed. Verified with 5 consecutive successful fetches under active daemon load.
- **Phase 2: web-configurable theme + screen visibility (2026-09-16, same-day follow-up)** — the dashboard's read-only `/api/state` gained a paired `GET`/`POST /api/config` for theme presets and per-screen visibility, plus a "Settings" card in `tools/web_ui/index.html`. New `device_config.{h,cpp}` (`g_theme`/`THEME_PRESETS[3]`/`visible_mask`, NVS namespace `"cfg"`); `theme.h`'s 6 non-semantic macros now read `g_theme` through `lv_color_hex()` instead of literals, so re-theming needed zero changes at any of `ui.cpp`'s ~135 `COL_*`/`THEME_*` call sites. Background is pinned true black in every preset — deliberately not themeable, since `splash.cpp`'s shared Splash/Copilot/Aurora canvas (gotcha #13) fills empty pixels with a hardcoded black literal outside this system, and `THEME_GREEN`/`AMBER`/`RED` are tuned specifically for a black background. Screenshot-verified after a real theme change: panel/accent/bar colors shifted, background stayed black, no artifact behind the pixel-art screens.
  - **Real crash risk caught before flashing, by a Plan-mode validation sub-agent, not found through testing**: `ui_cycle_screen()`'s traversal loop (`ui.cpp`) was an unbounded `do/while(true)`, safe today only because `screen_is_populated()`'s `default:` case always returns `true` for several screens. ANDing a user-supplied visibility mask into that loop's exit condition — the naive design — meant an all-disabled mask (`{"mask":0}`, one `curl` away, or a corrupt NVS read) would spin `loop()` forever, starving `IDLE0` into a task-watchdog reboot loop that persists across reboots (the mask reloads unchanged from NVS every time). Fixed two ways: (1) `device_config_set_visible_mask()`/`device_config_init()` force-OR the Clock and Connectivity bits before persisting *and* after loading, so neither can ever actually go dark; (2) `ui_cycle_screen()`'s loop was converted to a bounded `for` (capped at `CYCLE_COUNT + 1` iterations) with a `SCREEN_CLOCK` fallback anyway, as defense-in-depth against a future predicate that goes all-false some other way. **Verified on-device**: a new serial QA command, `cycle` (exercises `ui_cycle_screen()` without a physical button), driven through `cfg 0 0` (all bits off) 15× in a row — the device correctly settled into a Connectivity→Splash→Clock loop and never rebooted.
  - **`screen_is_populated()` was deliberately *not* touched** to add the visibility check — it has two different consumers (`ui_show_screen()`'s null-container guard, gotcha #14's fix, vs. navigation's "should this be offered" question), and conflating them would have made the serial `screen <n>` QA command unable to reach a screen the user had hidden. A new `screen_in_cycle()` wrapper (`screen_is_populated() && device_config_screen_enabled()`) is used only by `ui_cycle_screen()`/`refresh_screen_dots()`; `ui_show_screen()`'s guard is untouched. Verified live: hiding CI's bit via `POST /api/config` (no restart) removed it from the `cycle` traversal immediately, while `screen 9` (CI's index) still jumped straight to it — then re-enabling its bit put it back in the cycle, still with no restart.
  - **A second, smaller bug found only through HTTP testing, not code review**: `handle_config_post()`'s restart flag was set from "did the caller ask for a different theme index" rather than "did the theme index actually change" — `POST theme=99` (out of range; `device_config_set_theme()` already silently clamps/ignores it) still reported `restart:true` and triggered a real `ESP.restart()` for a no-op change. Fixed by range-checking `theme` in the HTTP handler itself before deciding whether to restart, not just inside the setter. A concrete instance of the general lesson in this project's gotchas: a function silently rejecting bad input isn't enough if a caller two layers up still acts on the rejected value.
  - `POST /api/config` is form-encoded (`server.arg("theme")`/`arg("mask")`), not JSON like `/api/payload` — `WebServer` already parses `application/x-www-form-urlencoded` for free, so no `JsonDocument` is needed for two small fields; simpler and cheaper, though it means the two mutating routes now use two different body formats (a deliberate, documented tradeoff, not an oversight). A theme-change POST replies `200` *before* the device restarts (`ESP.restart()` from inside the handler would tear the TCP socket down before the response drains) — `restart_at_ms` in `web_server.cpp` defers it a beat, applied from `web_server_tick()`.
  - **Web page** (`tools/web_ui/index.html`): the dashboard is served open/unauthenticated and `GET /api/state` deliberately never exposes the auth token (gotcha-adjacent security boundary from the BLE-removal work) — so the Settings card's token comes from a `prompt()` the user fills in from the device's Connectivity screen, stored in `localStorage` (origin-scoped — re-entering it is required if the user switches between `clawdmeter.local` and a raw IP). `web_ui.h` grew from 2450 → ~4.1 KB gzipped; a total non-issue at 39.6% flash.
  - Static RAM: `59364` → `59396` bytes (`tools/check_static_mem.py`, well inside the 15% gate). Flash: `39.1%` → `39.6%`.
- **Security review + fix: `GET /api/screenshot.bmp` was unauthenticated and could leak the auth token (2026-09-17)** — an analysis pass over `web_server.cpp`/`wifi_net.cpp`/`device_config.cpp`/`tools/web_ui/index.html` found that the screenshot route was the one HTTP handler that skipped the `X-Auth-Token` check every other mutating/sensitive route has. That mattered because the Connectivity screen renders the token as on-screen text (`lbl_wifi_token`, `ui.cpp`) and nothing auto-returns the device to Clock — it can sit on Connectivity indefinitely (the normal post-provisioning workflow is "go to Connectivity, copy the token into the daemon config"). Anyone on the LAN hitting `/api/screenshot.bmp` during that window got the token in the clear, defeating the explicit "never expose the token over an unauthenticated route" contract already documented on `build_state_json()` and in the web UI's own comments. **Fix**: `handle_screenshot()` now checks `X-Auth-Token` first, same as `handle_payload()`/`handle_config_post()`. Since a plain `<img src="...">` can't attach a custom header, `tools/web_ui/index.html`'s screenshot card was reworked to `fetch()` the bytes with the header and hand the `<img>` a `URL.createObjectURL()` blob URL instead — and gated behind the same token-unlock flow as the Settings card (`shot-locked`/`shot-body`, sharing `updateLockUI()`), since it's no longer a route that works without the token. Rebuilt `web_ui.h` via `node tools/build_web_ui.js` after the HTML change — don't hand-edit that header.
  - Other findings from the same review, intentionally left as-is (documented tradeoffs, not bugs): `GET /` and `GET /api/state` are unauthenticated info-disclosure-by-design (usage/host stats, no secrets); the whole HTTP surface is plaintext (no TLS — infeasible on this heap budget, LAN-only threat model); `WebServer` buffers a POST body before a handler's token check can reject it, so an oversized unauthenticated body is a plausible heap-pressure DoS vector (not yet mitigated — would need a `Content-Length` cap ahead of the handler); the token comparison (`String::operator!=`) isn't constant-time (low practical risk given WiFi jitter and the token's keyspace). Revisit if the threat model ever moves off "trusted home LAN."

- **UDP discovery + remote screen navigation (2026-10-06)** — addressed two long-standing rough edges in one session: finding the device when its IP drifts (DHCP renewal, router reboot) without re-reading the Connectivity screen, and changing what's on the device's screen without walking over to press the physical button.   - **Verified end-to-end against the real device, not just compiled**: `tools/discover_device.py --timeout 5` found the live device by broadcast alone (`Found device at 192.168.1.69`). `POST /api/screen` was exercised directly over HTTP — `n=<idx>` round-tripped exactly (confirmed via a separate `GET /api/state` read-back), `action=next` advanced correctly along `CYCLE_ORDER` when tested back-to-back with minimal delay, and both a missing and a wrong `X-Auth-Token` were rejected with 401 before any screen mutation (confirmed by reading `handle_screen_post()`'s source: the token check is unconditionally first).   - **One isolated-test artifact worth remembering, not a bug**: during manual back-to-back `curl` testing, one `action=next` call landed one step "backward" from the expected `CYCLE_ORDER` position (`SysInfo`→`Copilot` instead of `SysInfo`→`VS Code`). Re-reading `handle_screen_post()`/`ui_cycle_screen()` confirmed the traversal table only steps forward and the auth check always precedes any mutation — the most likely explanation is a physical button press on the shared, desk-resident device landing between two of the test's own isolated HTTP calls (there's a real person at this desk; the device isn't a hermetic test fixture). A tighter back-to-back repeat (`n=1` then immediately `action=next`) reproduced the documented `Clock`→`Aurora` step cleanly. If a future session sees a one-off cycle-order mismatch while testing against the real hardware, suspect concurrent physical/serial access before suspecting the traversal code.
  - **Verifying an HTTP-triggered screen change via the serial `screenshot` command doesn't work** — opening the serial port resets the ESP32 (DTR/RTS toggle, see gotcha #9's sibling note in the `run` skill), which wipes out whatever screen the HTTP call just set before the screenshot command can even be sent. Any screenshot taken this way only proves the serial `screen <n>` path (already covered by prior sessions), not the HTTP path. Use `GET /api/state`'s `connectivity.screen` field (or the dashboard's own authenticated screenshot fetch, which goes over HTTP/fetch, not serial) to verify HTTP-triggered navigation instead.
